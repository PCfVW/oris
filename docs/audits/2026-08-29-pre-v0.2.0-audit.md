## P0 — must fix before v0.2.0

### F1. Unchecked size arithmetic silently under-allocates on a near-`usize::MAX` request {#f1}

**Ports:** `orisnik` + `orisnitsa`. **Reachable from:** every public surface (`oris_alloc`,
`GlobalAlloc::alloc`, `Allocator::allocate`, `std.mem.Allocator`, `Orisnik::alloc`).

`normalize_size`/`normalizeSize` is the first thing every tree-path request passes through, and it
rounds with a bare mask:

```rust
// Rust/src/align.rs
pub(crate) const fn round_up(value: usize, align: usize) -> usize {
    (value + (align - 1)) & !(align - 1)   // no overflow check
}
```

`alloc(usize::MAX)` is not small, so it reaches `Tree::alloc` → `normalize_size(usize::MAX)` →
`round_up(usize::MAX, 16)`:

- **Release build:** `usize::MAX + 15` wraps to 14, `14 & !15` → **0**. `Tree::alloc` then grows a
  64 KiB arena, splits at size 0, marks the block used, and returns its `mem()` to a caller who
  asked for `usize::MAX` bytes — guaranteed heap corruption on the first write.
- **Debug build:** an *arithmetic-overflow panic* instead, which violates the crate's own
  "OOM is a value, not an exception" rule (`Rust/CONVENTIONS.md`, Allocation Outcomes).

Zig behaves the same way: `std.mem.alignForward` is the same mask, so Debug/ReleaseSafe trips the
overflow safety check and ReleaseFast wraps.

**Reproduced** ([harness](#reproduction-harness)), all four combinations:

| Build | Call | Observed |
|---|---|---|
| `orisnik` release | `alloc(usize::MAX)` | returns `Some(ptr)`; `size(ptr)` = **0**; `allocated()` = 65536 |
| `orisnik` debug | `alloc(usize::MAX)` | panic: `attempt to add with overflow`, `Rust/src/align.rs:21` |
| `orisnitsa` ReleaseFast | `alloc(maxInt(usize))` | returns non-null; `querySize` = **0**; `allocated()` = 65536 |
| `orisnitsa` Debug | `alloc(maxInt(usize))` | panic: `integer overflow`, `std/mem.zig:4774` via `Zig/src/align.zig:26` |

**`calloc` is materially worse than `alloc` here, not merely adjacent to it.** `Orisnik::calloc`
uses `wrapping_mul` (deliberate, and documented as faithful to HPHA), then passes the *same wrapped
value* to `write_bytes` as the zero-fill length. So the wrapped size both under-allocates *and*
drives an immediate multi-exabyte memset:

| Build | Call | Observed |
|---|---|---|
| `orisnik` release | `calloc(2, usize::MAX)` | **segmentation fault** (exit 139) — 0-byte block, then `write_bytes(0, usize::MAX - 1)` |
| `orisnik` debug | `calloc(2, usize::MAX)` | panic: `attempt to add with overflow`, same site |

The `wrapping_mul` comment reasons that "an overflow changes what is allocated, never how much of
it gets zeroed" — which is true as written, and is exactly why this is fatal: the zero-fill length
stays faithful to a size the allocation no longer honours.

Other unchecked size sites on the same path:

- `Tree::grow` — `size + 3 * size_of::<BlockHeader>()`, then `round_up(_, PAGE_SIZE)`
- `Tree::alloc_aligned` — `grow(size + alignment)`
- `Tree::extract_aligned` — `size + alignment` and `size + alignment_offs`

**Fix:** one guard at the top of `Tree::alloc`/`Tree::alloc_aligned` — reject any `size` above
`usize::MAX - PAGE_SIZE - alignment` as `None`/`null`, before `normalize_size` runs. Cold path, no
hot-path cost. `calloc` additionally needs a checked `count * size` (this is a place to *stop*
being faithful to HPHA). Add boundary tests at `usize::MAX`, `usize::MAX - 8`, and
`calloc(2, usize::MAX)` on both ports.

### F2. `SECURITY.md` states F1 is already fixed {#f2}

**Ports:** documentation. The CWE table's first row reads:

> | **CWE-190** / **CWE-131** | Integer overflow / wrong buffer-size calc in a size + alignment
> request | Size and alignment are combined with **checked arithmetic** and the request is
> rejected (null / `error.OutOfMemory`) on overflow, before any allocation | always-on, cold path
> only — effectively free |

No such code exists in either port. Searching both trees for `checked_add`, `checked_mul`,
`saturating_*`, `@addWithOverflow` and `std.math.add` returns nothing on any size path.

The adjacent **CWE-476** row ("OOM is a **value**, never a panic") is contradicted twice: by F1's
debug panic, and by the always-on `assert!` in `os.rs`'s Windows `map` (which panics *inside an
allocator* if `VirtualAlloc` ever returns a non-64 KiB-aligned address).

**Fix:** implementing F1 makes the CWE-190 row true. Until then the row overstates what ships. The
`os.rs` assert is defensible, but `SECURITY.md` should note that the never-panic guarantee has
exactly one documented exception.

## P1 — high priority

### F3. `purge()` stops at the first partially-used bucket page; HPHA does not {#f3}

**Ports:** `orisnik` + `orisnitsa`. **Class:** fidelity + memory reclamation.

HPHA scans the whole page list and early-outs only on a *full* page:

```cpp
// hpha.cpp, allocator::bucket_purge
for (page* p = mBuckets[i].page_list_begin(); p != pageEnd; ) {
    if (p->mFreeList == NULL) break;   // full: stop
    page* next = p->next();
    if (p->empty()) { p->unlink(); bucket_system_free(memAddr); }
    p = next;                          // otherwise KEEP GOING
}
```

Both ports only ever inspect `front`, and break on *partial* as well as full:

```rust
// Rust/src/bucket.rs, Buckets::purge   (Zig/src/bucket.zig is identical in shape)
while let Some(front) = bucket.pages.front() {
    if unsafe { Page::is_full(front.as_ptr()) } { break; }
    if !unsafe { Page::is_empty(front.as_ptr()) } { break; }  // HPHA continues here
    ...
}
```

The in-code comment justifies this with *"pages are auto-sorted so a full page here means every
page after it is at least as full"* — but the auto-sort only fires on the full↔not-full
transitions (`Bucket::alloc` pushes to the back on becoming full; `Bucket::free` pushes to the
front on ceasing to be full). Ordering among *not-full* pages is arbitrary.

Reachable sequence:

1. Fill page A completely → A moves to the back; page B is created and pushed to the front.
2. Free one slot of A → A *was* full, so it moves to the front. List is `[A partial, B partial]`.
3. Free every slot of B → B was never full, so no re-sort. List is `[A partial, B empty]`.
4. `purge()` breaks on A. **B is never reclaimed.**

**Reproduced** ([harness](#reproduction-harness)) with `ELEM = 8` (8188 slots/page), in
`orisnik` release *and* debug and `orisnitsa` ReleaseFast *and* Debug — all four give the identical
result:

```
filled page A with 8188 slots; allocated = 65536
after 1 alloc on page B:      allocated = 131072
after purge():                allocated = 131072      <- HPHA gives 65536
```

Traced against `bucket_purge` by hand for the same list state: `p = A` → `A->mFreeList != NULL`
(partial), no break; `A->empty()` false, so advance; `p = B` → not full, `B->empty()` true →
`unlink()` + `bucket_system_free()`. HPHA reclaims B; both ports do not.

Consequence: `allocated()` stays above HPHA's after the same public sequence. That is a
"same final RSS" divergence — precisely what the v0.3.0 trace-corpus gate is meant to catch,
against the one reference it will be diffed with.

**Fix:** mirror HPHA — walk with an explicit cursor, capture `next` before unlinking, and continue
past partial pages. Must land in both ports in the same commit (cross-port invariant). Correct the
comment while there.

### F4. `Orisnik` is address-sensitive but movable in safe Rust {#f4}

**Ports:** `orisnik` (soundness hole in a safe API); `orisnitsa` has the same hazard, less sharply.

Three separate pieces of state bind to the instance's address:

- `IntrusiveList`'s lazily self-linked sentinel (`list.rs`)
- `IntrusiveMultiRbTree`'s ditto (`rbtree.rs`)
- `Bucket::marker()`, derived from `core::ptr::from_ref(self).addr()` and XOR-baked into every
  page it grows (`bucket.rs`)

`list.rs` and `rbtree.rs` both document *"callers must not move an `IntrusiveList` after the first
call to any of its methods."* That contract stops at the private-module boundary. `Orisnik`'s own
public doc carries `# Invariants` and `# Thread safety` and says nothing about movement; nothing in
the type enforces it (no `PhantomPinned`); and `Orisnik::new()` hands the caller an owned value:

```rust
let a = Orisnik::new();
let p = a.alloc(64).unwrap();
let b = a;                 // safe Rust, no unsafe, no warning
unsafe { b.free(Some(p)) } // sentinels dangle; every page marker now mismatches
```

The marker mismatch is the nastier half: `ptr_in_bucket` starts returning `false` for genuine
bucket pointers, so `free` routes them into `Tree::free`, which reads a `BlockHeader` out of the
bytes preceding a bucket slot.

**Reproduced** ([harness](#reproduction-harness)). Release: `size(ptr)` returns **64** before the
move and **0** after it — the query fell through to the tree path and read a `BlockHeader` out of
neighbouring bucket bytes. Debug is more interesting still:

```
thread 'main' panicked at Rust/src/bucket.rs:716:
assertion `left == right` failed: ptr_in_bucket's marker check disagreed with an
exhaustive page-list scan — see this function's own doc for the known,
HPHA-inherited cause
  left: false
 right: true
```

The codebase **already has the detector**. But its doc attributes a disagreement to HPHA's
inherited false-*positive* risk (a tree pointer whose bytes happen to read as a valid page
marker), whereas this is a false-*negative* from a moved instance — a different cause with a
different fix, currently mis-signposted for whoever hits it first.

**Fix (pick one):** add `PhantomPinned` and make the surface `Pin`-based; or make
`Bucket::marker()` a plain constant plus a per-instance counter rather than an address, and
self-link sentinels eagerly on first use. At minimum, state the non-move contract on `Orisnik`'s
and `Orisnitsa`'s *own public* docs, where a user will read it.

### F5. `alignment == 0` panics where HPHA accepts it {#f5}

**Ports:** `orisnik` + `orisnitsa`. **Blocks:** running Lazarov's `main.cpp` unmodified.

HPHA guards with `assert((alignment & (alignment-1)) == 0)`, which is **true** for zero — so
`realloc(ptr, 0, 0)` falls through `alignment <= DEFAULT_ALIGNMENT` into the plain `realloc`, which
frees. Both ports instead assert `alignment.is_power_of_two()` / `std.math.isPowerOfTwo(alignment)`,
both `false` at zero, so a debug or ReleaseSafe build aborts.

Not hypothetical: Lazarov's own `main.cpp` calls `gAllocator.realloc(tr[j].ptr, 0, 0)` in the final
loop of *TEST REALLOC with ALIGNMENT*. Any attempt to run his harness against Oris hits this on the
first pass. Same for `oris_realloc_aligned(h, p, 0, 0)` from C.

**Reproduced** ([harness](#reproduction-harness)) on that exact call:

| Build | Observed |
|---|---|
| `orisnik` debug | panic: `assertion failed: alignment.is_power_of_two()`, `Rust/src/orisnik.rs:210` |
| `orisnik` release | returns `None`, no panic (the `debug_assert!` is compiled out) |
| `orisnitsa` Debug | panic: `reached unreachable code` via `std.debug.assert` → `isPowerOfTwo` |
| `orisnitsa` ReleaseFast | returns null, no panic |

Note the shape of this: the harness runs *only* in optimized builds, and only because the check
disappears. That is the worst of both worlds — the assertion never protects a release user, and it
blocks the one workload that would exercise the code.

**Fix:** treat `alignment == 0` as "no alignment requested" (route to the unaligned path, matching
HPHA) and keep the power-of-two assert for non-zero values. Two lines per port, plus a test.

### F6. A zero-length `realloc`/`remap` frees and then reports failure {#f6}

**Ports:** `Rust/src/global_alloc.rs`, `Zig/src/allocator.zig`.

`GlobalAlloc::realloc(ptr, layout, 0)` forwards to `Orisnik::realloc(Some(ptr), 0)`, which *frees*
and returns `None` → the impl returns null. Null from `GlobalAlloc::realloc` means "allocation
failed, your original pointer is still valid", so a contract-respecting caller will later
`dealloc` a pointer that is already free.

Zig's `remapImpl` has the identical shape, and its failure signal is even more load-bearing:
`null` from `remap` means "no advantage — do alloc+copy+free yourself", i.e. the caller is
explicitly told it still owns the memory. `resizeImpl` forwards to `Orisnitsa.resize`, whose
`std.debug.assert(size > 0)` aborts on a zero `new_len`.

**Reproduced** ([harness](#reproduction-harness)) — the slot is provably recycled, so the free
really happened:

```
alloc(64)                   -> 0x28fb21c0000
realloc(ptr, layout, 0)     -> 0x0            ("failed, ptr still valid")
next alloc(64)              -> 0x28fb21c0000  <- same slot handed back out
```

A caller that believed the null and later called `dealloc(p, layout)` would free a slot the
allocator has already re-issued to someone else.

Both are caller-contract violations rather than port bugs (`GlobalAlloc::realloc` requires
`new_size > 0`), but neither module says so and the guard is one line in each.

**Fix:** return null / `false` for `new_size == 0` without touching the pointer, and document the
precondition alongside the existing `dealloc` rationale comment.

## P2 — medium priority

### F7. A declared Zig test gate is never exercised {#f7}

`Zig/CLAUDE.md` pre-commit step 2 lists `std.testing.checkAllAllocationFailures` as part of the
verification gate, and `Zig/CONVENTIONS.md`'s *Verification gate* section repeats it. It appears
**zero** times across `Zig/src`. (`std.testing.allocator` is used — 38 sites — but that is leak
detection, not failure injection.)

This matters more than a stale doc line: `os::map` is not injectable in either port, so **every**
OOM early-out in `Tree` and `Buckets` — each `?` / `orelse return null` on the `system_alloc` path
— is unexecuted by any test in either language.

**Fix:** add a test-only failure-injection seam at `os::map` (a counter that fails the *n*th call),
then either honour the `checkAllAllocationFailures` claim or drop it from both docs. The seam pays
for itself again at v0.2.0, when leak detection needs the same hook.

### F8. `Cpp/NOTICE.md`'s "Modifications: None" is off by one line, and the v0.2.0 reference is ambiguous {#f8}

`Cpp/NOTICE.md` states the files are *"byte-identical to the maintainer's archived 2007 originals,
modulo file timestamps."* Diffed against `hpha.zip`'s contents:

| File | vs. archived original |
|---|---|
| `Cpp/hpha.cpp` | ✅ byte-identical |
| `Cpp/hpha.h` | line 31: `#define MULTITHREADED` → `//#define MULTITHREADED` |

The change is obviously right for this project (both ports are single-threaded), but the NOTICE is
the provenance document, so it should record it. One sentence under *Modifications*.

**The more consequential half:** the `hpha-errata/` copy is a *later* (2012-04-21) revision that
differs in the `DEBUG_ALLOCATOR` surface — exactly what v0.2.0 ports. **Decide now which C++
variant v0.2.0 is a port of**, and say so in `Cpp/NOTICE.md`; otherwise the milestone starts
against an undeclared reference.

> **Correction (added while acting on this, 2026-08-29).** The sentence above originally said the
> 2012 revision "refactors `debug_replace_begin`/`debug_replace_end` into a single
> `debug_replace`". That is **backwards**, and the error mattered. Re-diffed against the archived
> 2011 source package: `Cpp/` (and that archive) carry the *single* `debug_replace`; the 2012
> revision *splits* it into `replace_begin`/`replace_end`.
>
> The direction matters because the split is a **bugfix**, not a refactor. Two of `realloc`'s
> three debug call sites pass `newPtr` into `debug_replace` with no null check, and both
> `bucket_realloc` and `tree_realloc` can return `NULL`; the 2007 form's unconditional
> `*record = debug_record(newPtr, ...)` then destroys the record of the **still-live original**
> allocation. The 2012 `replace_end` guards it with `if (ptr)`. So the source this repo carries
> has a debug-allocator defect the author later fixed, and v0.2.0 is about to port it.
>
> Recorded as **E9** in [`Cpp/ERRATA.md`](../../Cpp/ERRATA.md), with the recommendation to port
> the 2012 form.

**Also worth pinning:** `Cpp/hpha.h:26–29` reads `#ifdef _DEBUG` / `#define DEBUG_ALLOCATOR`. Any
MSVC *Debug* configuration silently turns `MEMORY_GUARD_SIZE` from 0 to 16, which shifts every
size class and every split. `Cpp/oracle/README.md`'s build line dodges this by accident; it should
say so explicitly, and so should whatever harness v0.2.0 adds.

### F9. The suites cover shape, not scale — and the top surface is outside Miri {#f9}

79 Rust and 81 Zig tests, all green, all well-written. But they are almost entirely small
hand-authored scenarios:

- The only randomized or differential test in either repo is
  `rbtree::pseudo_random_insert_erase_stress_matches_btreemap` — the *data structure*, not the
  allocator. Nothing randomized ever calls `alloc`.
- The largest live-allocation count reached *through the public allocator* is **2000** (the
  `ArrayList`/`Vec` smoke tests in `allocator_trait.rs` / `allocator.zig`). One `Bucket`-level test
  goes higher — `bucket_alloc_sorts_full_page_behind_partial_page` exhausts 255 slots — but against
  a `FakePage`, not through `Orisnik`. Nothing exercises multi-arena growth, repeated arena purge,
  or the LIFO-vs-FIFO free orders that shake out coalescing.
- No boundary tests on the size-class edges: 0, 1, 8, 255, 256, 257, `MIN_BLOCK_SIZE`,
  `SPLIT_REMAINDER_MIN`, `usize::MAX`. **F1 sits in that gap.**
- `free_with_size`/`free_with_size_aligned` get one happy-path test each. The hazardous cases their
  own doc comments describe at length (a post-`realloc` size; `orig_size == 0` with a non-null
  pointer, which underflows `bucket_spacing_function`) are untested.
- 26 of 83 Rust tests are Miri-ignored. Four of those are `os.rs`'s permanent, well-argued
  exception (Miri shims neither `VirtualAlloc` nor the partial-`munmap` trim), so the real figure
  is **22 allocator-path tests outside the soundness gate**, distributed like this:

  | Module | Miri-ignored / total |
  |---|---|
  | `orisnik.rs` | 9 / 13 |
  | `bucket.rs` | 5 / 10 |
  | `global_alloc.rs` | 3 / 3 |
  | `capi.rs` | 2 / 3 |
  | `allocator_trait.rs` | 2 / 3 |
  | `tree.rs` | 1 / 12 |

  The split is not arbitrary, and it is sharper than the raw counts suggest: **every top-surface
  test that actually allocates is ignored.** The six that survive are exactly the ones that never
  reach `Buckets`/`Tree` at all — `alloc_zero_returns_none`, `realloc_none_ptr_acts_as_alloc_of_zero`,
  `size_and_resize_of_null_are_zero`, `free_of_null_is_a_no_op`, `oris_destroy_on_null_handle_is_a_no_op`,
  and `zero_size_layout_returns_dangling_without_touching_the_os`. `bucket.rs`/`tree.rs` earned
  their coverage by building `FakePage`/`FakeArena` seeding seams; the dispatcher has none, so no
  real allocation on any public surface is ever seen by Miri.

**Fix:** one `FakeArena`-style seam at the `Orisnik`/`Orisnitsa` level moves the whole top surface
under Miri. Then the stress test in the next section. Both are worth doing *before* v0.2.0 — the
debug allocator layers on top of this code, and a bug underneath will read as a bug in the new
instrumentation.

## On running Lazarov's `main.cpp`

Short answer: **yes, and it is worth doing — but not as a test suite, because it isn't one.**
`hpha-errata/main.cpp` contains no assertions at all. Its six cases print timings and nothing
else; its only correctness signal is "did not crash." The value is in its *shape*, and there are
three quite different ways to extract that, worth quite different amounts.

*(Note: `hpha-errata/main.cpp` is byte-identical to the `hpha.zip` original — unlike the `.h`/`.cpp`
in that directory, it carries none of the errata edits.)*

### What it actually exercises

`benchmark1()` runs six cases against HPHA and the CRT side by side: alloc/free,
alloc/free-with-size, the same two with alignment, then realloc and aligned realloc. `N` is
512 Ki records. `rand_size()` returns 2–4096 bytes with an `r^8` skew toward the floor, so the
great majority land on the bucket path and a long tail crosses into the tree. `rand_alignment()`
returns `1 << (0..7)` — so 1, 2 and 4 as well as 8–128. `benchmark2()` is a C++
operator-`new` exposition, not allocator coverage; skip it.

Every one of those calls has an exact `oris.h` counterpart, already exported and already linked in
CI by `c-abi-ci.yml`:

| `main.cpp` | `include/oris.h` |
|---|---|
| `alloc(size)` | `oris_alloc` |
| `alloc(size, alignment)` | `oris_alloc_aligned` |
| `free(ptr)` | `oris_free` |
| `free(ptr, size)` | `oris_free_with_size` |
| `free(ptr, size, alignment)` | `oris_free_with_size_aligned` |
| `realloc(ptr, size)` | `oris_realloc` |
| `realloc(ptr, size, alignment)` | `oris_realloc_aligned` |

I checked the one place this mapping could quietly break: `free(ptr, size, alignment)` with the
sub-`DEFAULT_ALIGNMENT` values `rand_alignment` produces. `alloc_aligned` routes alignment ≤ 8
through `alloc` (`clamp_small_allocation`), while `free_with_size_aligned` computes
`bucket_spacing_function(round_up(orig_size, old_alignment))` — two visibly different expressions
that must land on the same bucket index or the free corrupts a size class. Brute-forced over all
**2304** pairs (sizes 1–256 × alignments 1, 2, 4, …, 256): **0 mismatches**. The round-trip is
safe. **F5 is the one real blocker**, and it fires on the last loop of the aligned-realloc case.

One adjacent hazard the same brute force surfaced, which `main.cpp` does *not* hit but a C caller
easily could — `oris_free_with_size(h, p, 0)` on a live pointer. `is_small_allocation(0)` is true,
so it reaches `bucket_spacing_function(0)` → `((0 + 7) >> 3) - 1` → underflow to `usize::MAX`.
Reproduced:

| Build | Observed |
|---|---|
| release | panic: `index out of bounds: the len is 32 but the index is 18446744073709551615`, `Rust/src/bucket.rs:667` |
| debug | panic: `assertion failed: size > 0 && size <= MAX_SMALL_ALLOCATION`, `Rust/src/bucket.rs:73` |

Rust's array bounds check contains it, so **in `orisnik` this is a panic, not memory
unsafety** — but it is still a panic on a free path in a crate whose lint floor sets
`panic = "deny"` and `indexing_slicing = "deny"`.

> **Correction (added while fixing this, 2026-08-29).** The sentence above is right about
> `orisnik` and wrong to stop there. `orisnitsa` was not tested at the time. It has no
> bounds check in `ReleaseFast`, and probing it afterwards showed the call returning
> **with no trap at all** — an out-of-bounds index into `self.buckets` followed by a write
> through whatever it landed on, in the build users ship. There are also **three** entry
> points, not one: `free_with_size(p, 0)` and both zero-size forms of
> `free_with_size_aligned`. Tracked and fixed as **F10** in v0.1.1. Worth noting *why* it slipped through: `bucket.rs:667` carries
`#[allow(clippy::indexing_slicing)]` justified as "`bi < NUM_BUCKETS`, checked above" — but the
check above it is a `debug_assert!`, which is exactly what a release build removes. The `allow`
rests on a premise release builds do not uphold. HPHA has the identical hole (its own
`assert(ptr_in_bucket(ptr))` is likewise debug-only). Cheap to close alongside F1.

### Option A — port it to the C ABI and run it as-is

*Low cost, low information.* Mechanical: swap `gAllocator.x(...)` for `oris_x(h, ...)`, keep the
timing loops. Replace `_aligned_malloc`/`_aligned_realloc` on the comparison side (MSVC-only;
`posix_memalign` elsewhere, and there is no portable aligned-realloc, so that leg becomes
alloc+copy+free).

What you get is a wall-clock number against the system allocator — a v0.3.0 benchmark deliverable,
not a v0.2.0 one, and the ROADMAP already commits to mimalloc-bench for that, which is a far better
harness. What you *also* get, immediately, is whether 512 Ki live allocations survive at all. Worth
one manual run on Windows for that alone; not worth wiring into CI.

### Option B — use it as a three-way differential oracle

*High value; defer to v0.3.0.* This is the version worth planning for, and it fits the ROADMAP
better than it first appears. `main.cpp` is already deterministic — `srand(1234)` before every case
— which is exactly the property the v0.3.0 trace corpus needs, arrived at from a workload someone
actually designed rather than a synthetic generator.

Instead of comparing timings, record per-operation state — `(op, size, alignment, allocated(),
size(ptr))` after each call — and diff C++ ⇄ Rust ⇄ Zig, the same three-way pattern `Cpp/oracle/`
already established for the RB-tree. Two things must be settled first:

- **`rand()` is not portable.** MSVC's LCG is not glibc's. Don't try to run the three in lockstep
  from their own `rand()` — record the C++ side's op stream to a file once, and have both ports
  *replay* it. That recorded file is literally the v0.3.0 trace format, and deriving the format
  from a real trace beats designing it in the abstract.
- **Build configuration is load-bearing.** Per F8: build without `_DEBUG`, or `MEMORY_GUARD_SIZE`
  becomes 16 and every size class shifts; and `MULTITHREADED` differs between the `Cpp/` copy and
  the `hpha-errata/` copy. Same-config builds only, stated in the harness README.

### Option C — reimplement its shape as a native stress test in each port

*Cheapest, highest immediate return.* No C++ in the loop at all. Take the structure — 512 Ki
allocations at `r^8`-skewed sizes, freed in the randomized `j = i + rand() % (N - i)` order, then
the realloc phase — swap `rand()` for an inlined LCG with a fixed seed so both ports generate the
identical stream, and **add the assertions `main.cpp` never had**: write a per-allocation byte
pattern derived from the index, verify it on free, assert `allocated() == 0` after `purge()`.

Roughly 80 lines per port; runs in seconds. It closes most of F9 on its own, it is the exact
workload class the current suites never touch, and — checking reachability by hand — it would have
surfaced both **F1** (the size tail crosses into the tree path constantly) and **F3** (the
randomized free order produces partial-then-empty page lists routinely, after which `purge`
under-reclaims and the final `allocated() == 0` assert fails).

### Recommended order

1. **Fix F1 (including the `calloc` half), F3 and F5 first.** They are cheap, they are all in code
   v0.2.0 builds on top of, and F5 is what stops `main.cpp` running at all. `calloc`'s wrapped
   zero-fill is the one to do first — it is the only finding here that crashes the process
   outright rather than corrupting quietly.
2. **Do C now**, before the debug allocator. Cheapest confidence you can buy in the layer
   underneath, and the regression net for the fixes above.
3. **Do A once, manually, on Windows** — documented next to `Cpp/oracle/`, not in CI, for the same
   Win32-only reason that harness already cites.
4. **Write B down in the ROADMAP under v0.3.0**: `main.cpp` is the trace-corpus seed, and
   recorded-replay (not `rand()`-in-lockstep) is how it gets used.

### One more thing about v0.2.0

HPHA's real correctness oracle was never `main.cpp` — it was `DEBUG_ALLOCATOR` itself: guard
bytes, the record map, and `check()`. That is precisely what v0.2.0 ports. So the milestone
*delivers* the assertion layer `main.cpp` lacks, and the natural sequencing is: option C's stress
workload, then v0.2.0's `check()` running underneath it.

## What was checked and found sound (no action)

- **Tree-path fidelity.** `tree_extract_aligned`'s `lower_bound`/`upper_bound` walk — including
  which node is and is not fit-checked, and the `bestNode == lastNode → next()` removal-time trick
  — matches `hpha.cpp` exactly. So do `tree_attach`/`tree_detach`'s MR-cache hand-off,
  `coalesce_block`'s next-then-prev order, `tree_realloc_aligned`'s four-branch cascade, and
  `tree_purge`'s double `tree_attach(NULL)`.
- **The deliberate upstream-bug fix.** The `elem_size.min(size)` copy cap in the bucket→tree
  aligned-realloc path is a genuine heap-overflow fix over the 2007 original, correctly reasoned as
  not touching the state-transition invariant, and mirrored identically in both ports.
- **Cross-port dispatch parity.** Every branch compared matches, including the subtle one: Rust
  shadows `size` with the clamped value *inside* the `ptr_in_bucket` block while Zig uses a
  separate `sz` binding — different idioms, identical scoping, so the tree fall-through in both
  uses the unclamped value, as HPHA does.

- **CI structure.** Three-OS matrices, MSRV lane, the nightly-feature lane, the C-ABI smoke job
  with its header-drift diff, and the by-name aggregator gates (with the empirical note on why

## Reproduction harness

Findings F1 and F3–F6, plus the `free_with_size(ptr, 0)` note, were executed rather than argued.
The harness lived entirely **outside the repository** — a scratch Rust crate with
`orisnik = { path = "…/Oris/Rust" }` and a scratch Zig module importing `…/Oris/Zig/src/root.zig`
— so nothing under version control was built into, modified, or relocked. Confirmed after the
fact: `git status` showed only this document, and `Rust/Cargo.lock` was unchanged.

Each finding was run in **both** a checked profile (`cargo build` / `-Doptimize=Debug`) and an
optimized one (`--release` / `-Doptimize=ReleaseFast`), because several of these behave
*differently* in the two — and in F5's case the difference is the finding.

| Check | Ports exercised | Result |
|---|---|---|
| F1 `alloc(usize::MAX)` | Rust + Zig, both profiles | reproduced (0-byte block / overflow panic) |
| F1 `calloc(2, usize::MAX)` | Rust, both profiles | reproduced (**segfault** in release) |
| F3 purge divergence | Rust + Zig, both profiles | reproduced (131072, expected 65536) |
| F4 move hazard | Rust, both profiles | reproduced (`size` 64 → 0; existing `debug_assert` fires) |
| F5 `realloc_aligned(p, 0, 0)` | Rust + Zig, both profiles | reproduced (panics only in checked builds) |
| F6 `GlobalAlloc::realloc(p, l, 0)` | Rust, release | reproduced (slot address recycled) |
| `free_with_size(p, 0)` | Rust, both profiles | reproduced (bounds-check panic) |
| Bucket-index round-trip | arithmetic model of both ports | 2304 pairs, 0 mismatches |

Reconstructing it is a few minutes' work: a `Cargo.toml` with a path dependency on `Rust/`, and a
`build.zig` creating a module rooted at `Zig/src/root.zig`. Every call used is on the public
surface — no internals were reached into, and no port source was patched to make a finding appear.
That matters for F3 and F4 in particular: both are reachable by a caller doing nothing unusual.
