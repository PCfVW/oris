## P0 — release blockers

### G1. Version numbers are still 0.0.0 everywhere the release will read them

- [`Rust/Cargo.toml:3`](../../Rust/Cargo.toml) — `version = "0.0.0"`
- [`Zig/build.zig.zon:9`](../../Zig/build.zig.zon) — `.version = "0.0.0"`
- [`Rust/src/lib.rs:33`](../../Rust/src/lib.rs) — `html_root_url = ".../orisnik/0.0.0"`

Tagging `v0.1.0` today would: (a) fail `cargo publish` (0.0.0 already exists on
crates.io — a lucky failure mode, but it kills the ceremony halfway with the Zig
release possibly already created), and (b) ship a Zig tarball whose manifest claims
0.0.0 under a v0.1.0 tag — a *silent* lockstep violation, since `zig-release.yml`
has no version check at all.

**Fix:** bump all three before tagging, **and** add a tag↔manifest consistency step to
both `rust-publish.yml` and `zig-release.yml` (fail if `${GITHUB_REF_NAME#v}` ≠
manifest version) so the mismatch can never ship silently again.

### G2. The "release ceremony" is referenced but documented nowhere

[`README.md`](../../README.md) says v0.1.0 is ready "once the release ceremony runs,"
but no file records what that ceremony is. Reconstructed from the repo, one tag push
must be preceded by at least:

1. Version bumps (G1: `Cargo.toml`, `build.zig.zon`, `html_root_url`).
2. `CHANGELOG.md`: move `[Unreleased]` into a dated `## [0.1.0]` section (the HTML
   comment anticipates this).
3. `SECURITY.md`: supported-versions table (`main` pre-release → `0.1.x` supported)
   and the "as of this writing" blockquote.
4. Status paragraphs in three READMEs (root "Not yet released… ready to tag",
   `Rust/README.md` "not yet published", `Zig/README.md` "not yet tagged").
5. Full local gauntlet incl. Miri (see G5) on the exact commit to be tagged.
6. `git tag vX.Y.Z && git push --tags` → both workflows fire.
7. Post-release: verify crates.io/docs.rs/Release pages, badges resolve.

**Fix:** write `RELEASING.md` (or a `docs/` equivalent) capturing this checklist.
Six documents carry release-state prose; without a checklist some will drift stale.

## P1 — high priority

### G3. The single-threaded-UB contract is invisible on the published doc surface

`Orisnik` is `unsafe impl Sync` purely to occupy a `#[global_allocator]` slot;
[`Rust/src/global_alloc.rs:6-16`](../../Rust/src/global_alloc.rs) states plainly that
installing it in a genuinely multithreaded program is **undefined behaviour**. But:

- That warning lives in a **private module's** doc comment and a `// SAFETY:` code
  comment ([`Rust/src/orisnik.rs:45-55`](../../Rust/src/orisnik.rs)) — neither is
  rendered on docs.rs.
- The quick-start in [`README.md`](../../Rust/README.md), the root README, and the
  `lib.rs` crate doc all show the `#[global_allocator]` pattern with **no caveat** —
  and nearly every real Rust program is multithreaded (the default `cargo test`
  harness included).

The "single-threaded" positioning is stated as a *performance* trait throughout the
prose; nowhere public is it stated as a *soundness contract* for this surface.

**Fix:** add a prominent warning (a) in the `lib.rs` crate doc next to the doctest,
(b) on the `Orisnik` type's public doc (it hosts the `GlobalAlloc` impl on docs.rs),
and (c) beside both README quick-starts. The Zig README quick-start deserves one
line too (the `std.mem.Allocator` it hands out is not thread-safe), though the
explicit-instance model makes it less of a trap there.

### G4. The `nightly` feature (`allocator_trait.rs`, 248 lines, 3 tests) has zero CI coverage {#g4}

`rust-ci.yml` builds stable/MSRV without `--features nightly`; the Miri lane runs
`cargo miri test` without it either. The third public surface advertised in the
README is never compiled, tested, or Miri-checked in CI — only locally. (It does
compile on current nightly; verified during this audit.)

**Fix:** add a small nightly CI job: `cargo +nightly test --features nightly` and
extend the Miri lane to `cargo miri test --features nightly` (Miri already runs on
nightly, so the feature costs nothing there).

### G5. The publish gauntlet omits Miri — the crate's own declared release gate

`SECURITY.md` and `Rust/README.md` present Miri as "a release gate, not just a
dev-time check", but [`rust-publish.yml`](../../.github/workflows/rust-publish.yml)
runs fmt/clippy/test/doc only. A tag pushed on a commit whose CI hasn't run (or
hasn't finished) publishes without the soundness gate ever executing on that commit.

**Fix:** either add the Miri job to the publish workflow, or gate `publish` on the
`Rust CI success` check for the tagged commit. (Same reasoning, weaker form, for
`zig-release.yml`, which tests Debug/ReleaseSafe but skips the ReleaseFast lane CI
treats as required.)

## P2 — medium priority

### G6. C-ABI linkability is not regression-tested in CI

`zig-ci.yml` runs only `zig build test` — the library artifacts are never even
*built* in CI (only `zig build` builds them, and only the release workflow's
packaging step touches the files, without compiling them). No workflow links a real
C caller against either port's artifacts. This is exactly the failure mode the
project already hit once (the empty-export-table DLL recorded in
[`CHANGELOG.md`](../../CHANGELOG.md) and [`Zig/build.zig`](../../Zig/build.zig) —
caught manually with `dumpbin`). The guard against its recurrence is currently a
comment.

**Fix:** add a CI step per port that builds the artifacts and compiles+runs a tiny C
smoke test against `include/oris.h` (a dozen lines: `oris_new`/`alloc`/`free`/
`purge`/`allocated`/`destroy`). This also turns the header↔implementation parity
check from convention into a gate.

### G7. `oris.h` ships in neither package

The crates.io package can't include `../include/oris.h` (outside the package root —
confirmed via `cargo package --list`), and the Zig tarball's `paths` list omits it.
Both READMEs tell C consumers to "pair with the shared include/oris.h", which only
exists on GitHub `main` — not versioned with what they installed.

**Fix:** either vendor a copy into each port (with a CI diff-check against the
canonical `include/oris.h`), or at minimum attach `oris.h` to the GitHub Release
alongside the Zig tarball and link it from both package READMEs.

### G8. The C++ oracle harness behind the cross-validation claim is not in the repo

The three-way RB-tree validation (C++ ⇄ Rust ⇄ Zig, 3000 steps byte-identical) is a
headline credibility claim in `CHANGELOG.md`, and
[`Rust/src/rbtree.rs:1317`](../../Rust/src/rbtree.rs) says the C++ companion is "not
part of this crate or its CI". The Rust/Zig trace emitters are checked in; the C++
side — the anchor of the whole chain — is reconstructible only from its description.

**Fix:** check the companion harness into `Cpp/` (e.g. `Cpp/oracle/`) with a
one-line build command in a README. It's also the natural seed for the v0.3.0 trace
corpus work.

### G9. The 64-bit-only restriction is documented only inside `block.rs`/`block.zig`

Both ports compile-error on 32-bit targets by design (a sound choice, well
justified in the module docs), but `README.md`, `INSTALL.md`, the Cargo metadata,
and the Zig README never mention it. A 32-bit or `wasm32` consumer discovers it as
a bare static-assert failure.

**Fix:** one line in `INSTALL.md` and each README's "What's here" (e.g. "64-bit
platforms only for v0.1.0 — see block.rs").

### G10. The Zig release tarball is packaged but never build-tested

`zig-release.yml` re-roots, tarballs, and hashes the package, but never extracts it
and runs `zig build test` from inside it — the one command that would catch a
missing `paths` entry or a re-rooting regression before consumers do.

**Fix:** add an "extract to temp dir, `zig build test` there" step between packaging
and release creation. Cheap, and it exercises the same layout `zig fetch` consumes.

## P3 — low priority / polish

- **G11.** "Working draft — v0.4" atop `README.md` and `BRIEF.md` reads, to an
  outside visitor, like a *project* version sitting next to "v0.1.0" claims.
  Reword ("Document revision 0.4") or drop from the README at release.
- **G12.** [`ROADMAP.md`](../../ROADMAP.md) v0.1.0 documentation bullet says
  "`LICENSE` (Apache-2.0)" — stale; the project is dual MIT OR Apache-2.0.
- **G13.** `Rust/Cargo.lock` is untracked and `.gitignore:4` ignores every
  `Cargo.lock`. The Cargo Book's own guidance here is explicitly neutral ("whether
  you do is dependent on the needs of your package") rather than a blanket
  recommendation either way, so this is a judgment call, not a correctness gap —
  flagged only because committing it would pin the Miri/nightly CI lanes against
  dependency drift (low risk today: `libc` is the only dependency) and make
  `git bisect` reproducible across contributors.
- **G14.** `CHANGELOG.md`'s `[Unreleased]` heading has no link definition
  (Keep-a-Changelog convention is a compare-URL per section); renders as literal
  brackets on GitHub.
- **G15.** The Zig package (`build.zig.zon` `paths` / release tarball) excludes
  `Zig/README.md` — installed package directories carry no documentation.
- **G16.** [`Rust/CLAUDE.md`](../../Rust/CLAUDE.md) pre-commit step 2 says
  `cargo clippy --all-targets --all-features` — a guaranteed hard error on the
  stable toolchain (the `nightly` feature is nightly-only by design) and stricter
  than what CI runs. Split into stable and nightly variants.
- **G17.** `BRIEF.md` reference 1 (Máchal) still carries "(Page range to be added
  once verified…)" — the document flags this itself; fine to ship, listed here so
  it isn't forgotten.
- **G18.** The crates.io package includes `CLAUDE.md`, `CONVENTIONS.md`, and
  `clippy.toml` (via `cargo package --list`). Harmless — flag only if a leaner
  package is preferred (`exclude` in `Cargo.toml`).

## What was checked and found sound (no action)

- **License trail**: SPDX headers universal; root/`Rust/`/`Zig/` license files
  present and consistent; `Cpp/NOTICE.md` provenance chain (GPG 7 → O3DE →
  author correspondence) coherent; `Cpp/` headers preserved verbatim as required.
- **CI structure**: 3-OS matrices, MSRV lane, aggregator gates, concurrency groups,
  Trusted Publishing (no stored token), tag-filter excluding pre-release tags,
  Dependabot for actions + cargo — all well-constructed.
- **API surface parity**: `oris.h`'s 14 prototypes match both `capi` implementations
  in name, signature order, and documented null/zero-size semantics; the
  ROADMAP-promised public API (`alloc`…`allocated`, aligned + naive variants) is
  complete on both sides.
- **Safety discipline**: every `unsafe` block seen carries a SAFETY comment; OOM is
  a value on every path; `wrapping_mul` in `calloc` documented as a faithful HPHA
  port; the one deliberate upstream-bug fix (`elem_size.min(size)` copy cap) is
  mirrored in both ports with matching invariant-impact analysis.
- **Cross-port invariant hygiene**: dispatcher logic, size-class math, and the
  64-bit layout gates are mirrored; deviations are annotated with their invariant
  impact in both ports.
