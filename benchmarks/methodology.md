# Benchmark methodology

How Oris is measured, so that a number in [`results/`](results/) can be reproduced, and
read for what it is. Two complementary benchmarks:

1. **Trace replay** — the project's own. A million-operation allocation trace
   ([`examples/traces/GRAMMAR.md`](../examples/traces/GRAMMAR.md)) is replayed through each
   allocator in-process. Same calls, same order, for every allocator: the purest comparison
   of the allocators themselves, on the workloads Oris was built for.
2. **mimalloc-bench** — the standard external harness. Real programs (a factoring program,
   a logic minimizer, an n-body simulation, allocator stress tests) run on each allocator
   through `LD_PRELOAD`. Closer to how an allocator is felt in practice, Linux only, and
   for Oris filtered through a shim (see below).

The shape follows the [priority-queue project](https://github.com/PCfVW/d-Heap-priority-queue)'s
protocol: a pinned input corpus, one process per measurement cell, warm-up then median of
N with the interquartile range, every result file carrying its own environment.

## Goals, and what is out of scope

- **Goal:** where Oris stands against the allocators people actually use, on its target
  workloads (`BRIEF.md`: many small, short-lived allocations, a few large buffers, one
  thread), and on general ones.
- **Out of scope:** multithreaded scalability (Oris is single-threaded until v2.x; the
  shims serialize threads, and the tables say so); tuning (every allocator runs with its
  defaults); and claims beyond the machines measured.

## 1. Trace replay

### Inputs

The bench tier of [`traces.toml`](traces.toml): seven traces of about one million
operations each — `planner` (the brief's GOAP workload), `parser`, and five synthetic
profiles (`small`, `large`, `mixed`, `aligned`, `realloc`). They are generated by
[`scripts/tracegen`](scripts/tracegen/README.md), deterministically and identically on
every OS; their SHA-256s are committed in [`trace-checksums.txt`](trace-checksums.txt), and
`tracegen verify` (run by `scripts/run.*` before measuring, unless `--skip-build` /
`-SkipBuild` is given) refuses to proceed if a regenerated trace differs.

### Allocators

| Harness | Allocators | Notes |
|---|---|---|
| [`scripts/bench-rust`](scripts/bench-rust/) | `orisnik`, `system`, `mimalloc`, `jemalloc`, `snmalloc` | Each through its `GlobalAlloc` impl, called directly — never installed as the process's global allocator. `jemalloc` does not build with MSVC and `snmalloc-sys` did not build on the Windows machine, so the Windows tables have `orisnik`, `system` and `mimalloc` only. |
| [`scripts/bench-zig`](scripts/bench-zig/) | `orisnitsa`, `smp` (`std.heap.smp_allocator`), `c` (`std.heap.c_allocator`) | Each through `std.mem.Allocator`'s raw functions. |

`orisnik` and `orisnitsa` are driven through their own API, so every trace operation means
exactly what it means to the transition record. The others have no counterpart for three
operations — `resize` (in-place), `size` and `purge` — which become, respectively, "report
the size already tracked", the same, and nothing. The last is not neutral: on the `planner` and
`parser` traces, which purge every few plans or files, Oris alone pays for returning idle pages
to the OS (and mapping them again), and alone gets the smaller resident set for it. Read their
Oris latency tails with that in mind. A plain allocation asks every allocator
for alignment 8, Oris's default.

### Procedure: three passes, each in its own process

The roadmap's "3-pass" protocol, made precise. For every (harness, allocator, trace):

| Pass | What runs | What is reported |
|---|---|---|
| **1. Wall time** | 2 untimed warm-up replays, then 10 timed replays | per replay, the time to run the whole trace; summarized as **median (IQR) [min–max]** |
| **2. Latency** | 2 untimed warm-up replays, then 1 replay timing every operation | the **p50, p99, p99.9 and maximum** per-operation time, and the timer's own median cost |
| **3. Memory** | 1 replay, no warm-up, in a fresh process | **peak resident-set growth** and **fragmentation** |

Within a process one allocator instance serves every replay; between replays, whatever the
trace left live is freed, untimed — so the warm-up leaves each allocator in its warm steady
state, Oris included (its pages stay mapped, as they would in a long-running program).

The trace is parsed into a flat operation array before anything is timed. Every
allocation gets one byte written per 4 KiB page (and a realloc's new tail likewise), as a
program filling its memory would; without this, untouched pages would never become
resident and the memory pass would measure nothing.

**Quartiles** use the exclusive-median method: Q1 and Q3 are the medians of the lower and
upper halves, the overall median excluded when the count is odd. The **mean is not
reported**: a single preemption can move it while the median stays put.

### The memory pass, precisely

- *Resident set* is `VmRSS` on Linux and the working set on Windows, sampled every 256
  operations, after every `purge`, and at the end. A peak shorter than 256 operations can fall
  between samples — an allocator that returns a large block to the OS at once is the one that
  benefits; on Linux, resetting `/proc/self/clear_refs` and reading `VmHWM` would be exact, and is
  the planned refinement. (On macOS only a lifetime peak is
  available; there is no macOS result yet.)
- *Peak resident-set growth* (RSS Δ) is the highest sample minus the sample taken just
  before the replay.
- *Fragmentation* is RSS Δ divided by the trace's **peak live requested bytes** (the largest
  sum of sizes the trace has live at once — a property of the trace alone). 1.0 would mean
  the allocator held exactly what the program asked for and nothing else; it includes every
  kind of overhead (headers, size-class rounding, free memory not returned, page
  granularity). For Oris, the peak of `allocated()` (bytes mapped) is also recorded.
- The harnesses' own memory never comes from an allocator under test: `bench-rust`
  installs a never-freeing bump allocator over memory mapped straight from the OS as its
  global allocator, and `bench-zig` allocates from `std.heap.page_allocator` only. Without
  this, the `system` allocator would find the harness's freed parsing buffers resident and
  reuse them, and appear to need almost no memory.

### Timing

`std::time::Instant` (Rust) and `std.Io.Clock.awake` (Zig): `clock_gettime(CLOCK_MONOTONIC)`
on Linux, `QueryPerformanceCounter` on Windows. **On Windows the counter ticks every 100 ns**,
so per-operation percentiles there are quantized to 100 ns and a fast operation reads as 0;
compare latencies within one platform, and prefer the Linux tables for the fast end.

### Build

Release builds, defaults otherwise: `cargo build --release` (`opt-level = 3`, thin LTO,
one codegen unit) and `zig build -Doptimize=ReleaseFast`; no PGO, no `-march=native`. The
comparison allocators are their crates' and Zig's defaults.

### Environment

`scripts/env.sh` (Linux, macOS) and `scripts/env.ps1` (Windows) record, once per run, the OS,
CPU, core count, RAM, CPU governor or power plan, `rustc` and `zig` versions, the commit
(and whether the tree was dirty) and the date — the host name is redacted. The record is
embedded in every result line, so each file stands alone. Recommended but not enforced: an
otherwise idle machine, on mains power, with a performance power profile.

### Running it

```sh
benchmarks/scripts/run.sh linux-x86_64                     # Linux / macOS
pwsh benchmarks/scripts/run.ps1 -Platform windows-x86_64   # Windows (Developer PowerShell)
(cd benchmarks/scripts/aggregate && cargo run --release)    # writes results/v0.3.0/SUMMARY.md
```

`--smoke` / `-Smoke` runs one trace once, to check the pipeline. Raw records go to
`results/<version>/<platform>/<harness>-<allocator>-<trace>-<pass>.jsonl`, one JSON object
per line with `schema_version: 1`.

## 2. mimalloc-bench

[mimalloc-bench](https://github.com/daanx/mimalloc-bench), pinned at commit
`391382606681` (2026-10-17), with two allocators added by
[`mimalloc-bench/bench.sh.patch`](mimalloc-bench/bench.sh.patch): `onik` and `onit`,
`LD_PRELOAD` shims over `orisnik` and `orisnitsa`
([`mimalloc-bench/preload-rust`](mimalloc-bench/preload-rust/),
[`mimalloc-bench/preload-zig`](mimalloc-bench/preload-zig/)). Each shim adds four things to
the allocator, and each is part of what is measured:

- **one global lock** around every call — Oris is single-threaded, so a multithreaded test
  measures Oris *serialized* (those rows are marked †);
- **16-byte alignment** for every request (`malloc` owes it; Oris's default is 8), by
  rounding sizes up to 16 and asking for `alloc_aligned(size, 16)`;
- **`malloc(0)` returns a unique pointer**, as glibc's does;
- **`fork` safety** for the lock (`pthread_atfork`).

Compared against glibc (`sys`), mimalloc (`mi`), jemalloc (`je`) and snmalloc (`sn`), as
mimalloc-bench builds them. Tests: mimalloc-bench's self-contained programs (`cfrac`,
`espresso`, `barnes`, `larson-sized`, `mstress`, `rptest`, `alloc-test`, `sh6bench`,
`sh8bench`, `xmalloc-test`, `cache-scratch`, `cache-thrash`, `glibc-simple`,
`glibc-thread`, `malloc-large`, `mleak`). The tests that build a large external project
(lean, redis, rocksdb, ghostscript, lua, linux, z3, spec) and `rbstress` (Ruby) are left to
the full run [`ROADMAP.md`](../ROADMAP.md) plans for v1.0.0. Each test runs three times;
the summary reports the median elapsed time and peak RSS, relative to glibc. Four tests run
for a fixed time and report throughput (`larson`, `rptest`, `xmalloc-test`, `glibc-thread`,
marked ‡): mimalloc-bench turns their throughput into a relative time, and their peak RSS
grows with the work done, so a slower allocator can look leaner.

```sh
benchmarks/mimalloc-bench/setup.sh            # once: clone, patch, build shims, allocators, tests
benchmarks/mimalloc-bench/run.sh linux-x86_64 # results/v0.3.0/mimalloc-bench/
```

## Reproducibility

Pinned: the traces (generator, seeds, exact `rand`/`rand_chacha`, and their checksums), the
mimalloc-bench commit and patch, the toolchains (recorded in every result), the build
flags. Not pinned: the comparison allocators' crate versions (`Cargo.lock` in each harness
records what was used), and the machine. Expect results within a few percent on similar
hardware; expect the *ranking* to hold far more firmly than any single number.
